Here's example Python code for token processing:

pythondef process_tokens(text, tokenizer):
    """Convert text to tokens and back."""
    tokens = tokenizer.encode(text)
    decoded = tokenizer.decode(tokens)
    return {
        "tokens": tokens,
        "token_count": len(tokens),
        "decoded": decoded
    }

# Usage
result = process_tokens("Hello, world!", tokenizer)
print(f"Tokens: {result['token_count']}")

What is inference?

Inference is the process of running a trained machine learning model on new input data to generate predictions or output. In the context of LLMs, inference means running the model to generate tokens based on a user's prompt.

Unlike training, which optimizes model weights, inference is about efficiently executing the model's computation graph for real-time predictions.

The key difference from training: inference is read-only, stateless per-request, and optimized for latency and throughput rather than accuracy.

Understanding tokens

Tokens are the atomic units that language models process. Each token represents a small chunk of text — roughly 4 characters of English text, though this varies by language and tokenizer.

Language models don't work with raw text; they work with token sequences. The tokenizer converts text into token IDs, and the model processes these sequences mathematically.

Understanding token flow is critical for capacity planning, latency analysis, and cost estimation. Token count directly impacts memory usage, computation time, and API costs.

Selecting the right model

Choosing a model involves trade-offs between performance, inference speed, memory requirements, and cost. No single model is best for all workloads.

Key factors to consider: model size (7B, 70B, 405B), architectural variants (base, instruction-tuned), quantization level, and inference latency requirements.

Smaller models are faster and cheaper but may lack reasoning capability. Larger models are more capable but require more resources. The right choice depends on your latency budget, cost constraints, and quality requirements.

Capacity planning basics

Capacity planning means estimating how much hardware you need to handle your expected throughput and latency requirements.

Start by understanding your workload: expected requests per second, average input length, desired output length, and acceptable latency. Then calculate memory requirements and GPU throughput capacity.

A common mistake is planning for peak load. You need capacity for sustained load plus headroom for bursts. Plan for 70–80% sustained utilization to leave room for traffic spikes.

Quantization fundamentals

Quantization reduces model precision (e.g., from FP32 to INT8) to decrease model size and memory bandwidth requirements.

Quantization can be post-training (after the model is trained) or during training. Post-training is simpler but may reduce quality. Quantized models are smaller, faster, and cheaper to serve.

The trade-off is accuracy loss. For many tasks, INT8 or even INT4 quantization works well. Some models degrade more than others with aggressive quantization.

KV cache optimization

Since KV cache is the primary memory bottleneck, optimizing it is crucial. Techniques include multi-query attention (MQA) and grouped-query attention (GQA), which reduce cache size by sharing keys/values across attention heads.

Another approach is KV cache quantization, storing cache in lower precision (INT8) instead of FP16, reducing memory by 2–4×.

Prefix caching stores attention outputs for reused prefixes (e.g., system prompts), eliminating redundant computation when the same prefix is used across multiple requests.

OpenAI-compatible API

Most modern LLM inference servers expose an OpenAI-compatible API, allowing drop-in replacement of OpenAI endpoints with local or self-hosted models.

The API supports chat completions, embeddings, completeness, and token counting. This standardization reduces migration friction and lets teams switch providers without rewriting application code.

OpenAI compatibility means client libraries (Python, JavaScript, etc.) work out of the box with just a URL and API key change.

Streaming vs. buffered

Streaming responses send tokens as they're generated, improving perceived latency. Users see the first token in ~100 ms instead of waiting for the entire response.

Buffered responses wait until the full response is generated, then send all tokens at once. Simpler to implement but higher perceived latency.

Streaming has trade-offs: clients need to handle partial responses, network overhead from more packets, and server complexity. For user-facing applications, streaming is usually worth it.
